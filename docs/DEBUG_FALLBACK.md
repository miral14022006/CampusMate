# Root Cause Analysis: Chatbot Fallback Bug

This document outlines the root causes discovered during reproduction and tracing (STEP 1) for the fallback message behavior ("I'm not quite sure how to answer that accurately...") on queries like "When is the exam registration deadline?" and "exam date".

## Evidence List

| Stage | Observed Value / Behavior | Why It Fails |
|---|---|---|
| **1. Intent Classification Model Loading** | `INTENT_MODEL_PATH` and `INTENT_VECTORIZER_PATH` point to `/data/index/intent_classifier.joblib` and `intent_vectorizer.joblib`. However, the Docker container does not mount `/data/index` with these files (or they were built under `/app/data/index`), causing `self.model = None` and `self.vectorizer = None`. | `predict()` immediately defaults to `{"intent": "out_of_scope", "confidence": 0.0, "is_fallback": True}` for all queries. |
| **2. DecisionPolicy Architecture** | In `DecisionPolicy.evaluate()`, rule 1 checks `if top1_intent == "out_of_scope" or top1_conf < self.t_low:` and immediately fires `_build_fallback()`. | Retrieval is treated as secondary to intent classification. Even when hybrid retrieval has strong evidence with reranker score > 6.0, the pipeline never reaches the retrieval score evaluation or answer generation. |
| **3. Evidence Gate on Retrieval** | DecisionPolicy compares `best_retrieval_score < self.min_retrieval_score (0.01)` using raw RRF score (~0.03) rather than normalized cross-encoder reranker score or dense cosine similarity. | The evidence gate uses raw RRF scores without normalization. If the threshold is misconfigured, valid documents get gated out. |
| **4. Short Query Slot Clarification** | For short or underspecified queries like `"exam date"`, the query lacks slots (e.g. `semester`), but because intent fell back to `out_of_scope`, `_check_missing_slot()` is never called, producing `FALLBACK` instead of `CLARIFY` with quick-replies. | DecisionPolicy falls back immediately instead of offering quick-reply clarification slots (e.g., "Sem 1", "Sem 3", "Sem 5"). |
| **5. Document Ingestion Path Discrepancy & Zero-Text Ingestion** | In production, `server` saves uploads to `/app/data/uploads` (mounted from host `/opt/campusmate/data/uploads`), but `nlp-service` had no mount for uploads. When `parse_document` is called or when scanned PDFs without text layers are uploaded, parsing yields 0 chunks. The server nonetheless marked documents as `processing_status: 'completed'` with `chunk_count: 0`. | Documents with 0 chunks silently show as "active" in admin, but are never indexed or searchable. Ingest and retrieval did not share common paths, and indexes were not hot-reloaded across memory instances. |
| **6. LLM Failure Fallback Behavior** | The configured Gemini key returned HTTP 404 (`models/gemini-1.5-flash:generateContent`), and `RAGEngine` caught the exception and called `answer_templater`. However, `answer_templater` required `score >= 0.12`, which raw RRF scores (~0.03) never satisfy, producing generic fallback string "For detailed information on this topic, please contact the student affairs office." | Pipeline/LLM errors masquerade as fallback/IDK responses, and extractive fallback fails to extract text from the top retrieved chunk. |
| **7. Duplicate Fallback & Raw Markdown** | `DecisionPolicy._build_fallback` formats `fallback_text = "\n".join(lines)` with `🏛️ **{contact['name']}**` and sets `clarification_question = fallback_text`. `AnswerStage` then assigns `context.answer = context.clarification_question`. | The client renders both or concatenates answer and clarification with unparsed markdown in certain views, and displays "This answer may not be grounded in a document" whenever `decision === 'FALLBACK'`. |
| **8. Contact Details Disclaimer** | `CAMPUS_CONTACTS_VERIFIED` defaults to `false`, causing `_build_fallback` to append "Verified contact details have not been configured for this deployment yet." | Exposes internal system setup status to students instead of providing neutral, student-friendly guidance. |
